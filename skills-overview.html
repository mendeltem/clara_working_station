01/39

auftrag-abarbeiten

● Usable

Works through a queued job in rounds: log first, trial run on two cases, result file, self-check against the acceptance list.

Loads when

A queued job with acceptance criteria, a rework note or a reviewer finding stands in the first message.

What it does

  • Starts each round from the job text and its log; writes a file after at most three read calls.
  • Runs a trial on two cases with a timeout, measures time, extrapolates; long runs go to the queue tools.
  • Writes the round log before the end and runs the acceptance check as the last tool call.
  • Keeps a job manifest with inputs, outputs and deviations; an unapproved deviation is asked, not made.

Strength

Each rule carries the counted cost that caused it, for example the number of rejected background commands, so the reason is visible.

Review findings

  • mediumIt names tools of the earlier gateway (patch, skill_view, a terminal tool); the current agent program offers edit_file, read_file and bash instead. Outdated content
  • mediumLimits such as the 420 s terminal cut-off were measured under the earlier gateway and may be outdated; the current shell tool has its own default timeout to check. Outdated content
  • mediumThe round procedure shares the file with incident history and a manifest specification; those two parts fit a reference file. Size and focus
  • lowFailure handling exists (obstacle into the log, return codes 3 and 4) but is spread over five sections; no single place answers 'a step failed'. Failure section
  • lowThe cost of one tool call is given as about a minute from a September measurement on the local model; with the current routing this may be outdated. Instructions

Proposed change

Replace the old tool names and limits with those of the current agent program and move incident history and manifest fields into reference files.

02/39

ziele-planen

● Usable

Turns a one-sentence goal that needs hours of work into a chain of checked, queued jobs instead of working it off in the chat.

Loads when

The researcher gives a one-sentence goal that needs more than a few minutes: research, compare, evaluate, 'overnight', 'for N hours'.

What it does

  • Sorts the request: a goal with work behind it is planned, a short question is answered, status is listed.
  • Asks at most one question on an unclear goal, then calls the planning tool with the researcher's wording.
  • Sets the project folder itself, avoids browsing the data tree and decides on the GPU flag.
  • Reports project, number of jobs with titles, result location and rough duration.

Strength

It says why long work must not run in the chat and gives one exact command, with a failure rule: report the last output line, do not rebuild the plan.

Review findings

  • mediumTwo rules on the GPU flag contradict: 'build, train, test' in the goal means set it, yet it is allowed only when the researcher explicitly permits the GPU. Instructions
  • mediumTwo rules on the project flag contradict: one says always set it and never leave the choice to the tool, the other says the tool chooses when no project is named. Instructions
  • mediumThe status section and the last sentence of the description duplicate laufstatus with a shorter, different procedure. Overlap
  • lowAfter planning there is no step that confirms the jobs are in the queue; the reply relies on the tool output alone. Check before done

Proposed change

Merge each pair of contradicting rules (GPU flag, project flag) into one rule and leave status questions to laufstatus.

▲ Needs work

Answers what is running: the state of jobs and projects.

Loads when

The researcher asks what is running, asks for an update, or asks where a job or project stands.

What it does

A fixed order of commands and a fixed answer shape: active work first with clock time, then waiting jobs, then totals quoted from the logs.

◷ Outdated

Stops autonomous work safely when the researcher says stop.

Loads when

Strength

It gives the reason for the stop order: the service goes first, or it pulls the next job while the session is being killed.

  • lowThe agent program now has a built-in tool that stops a work session; the skill does not say when to use the tool and when these steps. Overlap

◷ Outdated

Loads when

Questions on speed, crashes, GPU memory, context length, model change, restart or logs, or the researcher says it is slow or hangs.

Strength

  • mediumIt assumes the agent always thinks on the local model; the current agent reaches its model through a router that can also choose a hosted model. Outdated content
  • mediumThe context fix points to a branch in the start script that is no longer there; context sizes now stand in a model registry file. Outdated content
  • lowIt names three memory files of the earlier gateway, one of which no longer exists; these are statements, not commands, so it matters little. Outdated content

Proposed change

Rewrite it around the current chain (agent program, router, on-demand model start, watchdog) and remove every gateway command.

Loads when

Before measuring, comparing methods, starting a run over many cases, or when unsure about a tool.

◷ Outdated

Self-improvement: read the own session, draw one lesson, make one change, measure it, version it.

Loads when

The researcher says read your own session, what was expensive, learn from it, make a skill of it, or a task took over 15 minutes.

What it does

  • Chooses the form: a skill, a tool or a line in the lessons file; everything else only as a proposal.

Strength

  • lowA daily tool of the same name now exists and only reports; the skill does not say how the two relate. Overlap

Proposed change

Point reading, skill creation and commits at the session reader and skill folder of the current agent program, and commit only the changed file.

● Usable

Asks a question outside the machine through the exit guard, which blocks anything that refers to internal data.

Loads when

  • lowThe command now also has a plain web search and a page-text mode that the skill does not mention. Instructions

Merge the addendum into the main text so one current description of the command remains, and correct the log path.

dicom-nach-nifti

▲ Needs work

Converts DICOM series to NIfTI with a JSON sidecar, checks the geometry and keeps patient identifiers out of the sidecar.

Loads when

A request to convert scanner DICOM series to NIfTI, or a question on series, sidecars or patient identifiers in headers.

What it does

  • Finds DICOM folders, splits them into series and writes one NIfTI per series with SimpleITK.
  • Writes a JSON sidecar with acquisition fields and a CSV table with one row per series.
  • Checks slice count, voxel size and orientation against the DICOM header.
  • Keeps patient tags and full header dumps out of the sidecar.

Strength

Names the patient tags that must stay out of the sidecar and warns that the example script writes the full header.

Review findings

  • highThe sidecar field list includes the acquisition date, while the privacy section of the same skill lists the examination date among the identifying header fields. Instructions
  • mediumIt says dcm2niix is not installed; a dcm2niix binary now exists in one conda environment of the machine, so the statement and the choice of main route may be outdated. Outdated content
  • mediumRepetition, echo and inversion time are copied as stored in DICOM (milliseconds), while BIDS wants seconds; the English DICOM-to-BIDS skill has that conversion. Instructions
  • mediumOverlaps the English DICOM-to-BIDS skill; this one adds privacy rules, the slice-count check and a CSV log, but lacks the human-checked series table and duplicate checks. Overlap
  • lowNo failure section: the table has an error column, but nothing says what to do with a series that cannot be read or has missing slices. Failure section

Proposed change

Remove the acquisition date from the sidecar list, convert the three times to seconds, and re-check the statement that dcm2niix is missing.

nifti-pruefen

● Usable

Checks and repairs NIfTI files: readable, same grid as the mask, orientation, voxel size, header.

Loads when

Before any pipeline on image data, on gzip, shape or header mismatch errors, and for mask volume, centre of mass or lesion counts.

What it does

  • Tests that each file loads and prints shape, voxel size and orientation.
  • Repairs an unreadable file by rewriting it with fslmaths next to the original.
  • Compares two grids by corner offset in mm and fixes header-only differences with fslcpgeom.
  • Gives rules for mask volume in ml, centre of mass and 26-neighbour components.

Strength

The grid check compares corner offsets against a quarter-voxel tolerance instead of testing affines for exact equality.

Review findings

  • mediumStep 1 only calls nib.load, yet the skill's own trap list says that reads just the header; a truncated gzip file passes the first check. Check before done
  • mediumIt sends the agent to a skill named qc-mosaik for the overlay check; no skill of that name exists among the 39. Instructions
  • mediumIt tells the agent to call a helper command for volume and centre of mass; on disk only a script with a .py ending carries that name, so the call as written may fail. Instructions
  • mediumTwo jobs in one skill: file checks and repair, plus mask statistics (volume, centre of mass, components) that are buried in the list of traps at the end. Size and focus
  • lowThe pipeline library skill has a validate function that reads the whole gzip stream; this skill adds repair, header copy and the grid tolerance, which that text lacks. Overlap

Proposed change

Make step 1 read the data, not only the header, and move the mask statistics rules into their own section or reference file.

How the review was done

  • What was read. The instruction file of every skill in full, and the list of files in its folder, in four reading passes. Every finding rests on a passage of the skill file; a program checked that each such passage occurs there word for word. Some findings also rest on a read-only look at the machine: does a named tool, file or service still exist. No skill was run on a task.
  • The seven points. Description: says what the skill does and when to load it. Instructions: concrete steps and commands instead of general advice. Check before done: says how to verify the result. Failure section: says what to do when a step fails. Outdated content: tools, services or files that have changed since. Overlap: repeats what another skill already covers. Size and focus: one job per skill, long material in reference files.
  • The verdicts. Good: nothing of weight found. Usable: works, small gaps. Needs work: a gap that can make it fail or not load. Outdated: describes a setup that no longer exists.
  • What a verdict is not. A reading of the text, not a measurement. Whether a description really loads its skill has to be measured with test requests, and the four reading passes may differ a little in strictness. “May be outdated” in a finding means: the text points to a setup that has changed, and the step was not re-tested.
  • What is published. Only names, counts and hand-checked lines; the skill texts stay on the machine. The limits shown (1,024 characters for a description, 500 lines recommended for the instructions) are those of the Agent Skills specification.
